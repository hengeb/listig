# Masked reply addresses

`reply-to: masked-sender` / `masked-both`, the reply relay and the compose form.

**Relay beyond the masked modes.** The relay (`+r-` address) is active for every `reply-to` (`ReplyToBehavior::relayMode()`): `masked-both` keeps its group behaviour; all other modes (`masked-sender`, `sender`, `both`, `list`, `nobody`) relay *privately to the target only* (never moderated, not archived). On those lists a `+r-` address reaches a member only through the `{sender-reply-address}` variable (e.g. in the footer, [Variables](variables.md)) or the archive viewer's "reply to the author only" button ([Archive viewer](archive.md#archive-viewer)), which therefore never shows the author's address even though `sender`/`both` would send it along. A relayed mail's own `Reply-To` is the replier's token (anonymous back-and-forth) whatever the list's `reply-to` is.

## Masked reply addresses (`reply-to: masked-sender` / `masked-both`)

Like `sender`/`both`, but the sender's address never appears in the mail: `Reply-To` is `{list->localPart}+r-{TOKEN}@{domain}` (`MailProcessor::setOutgoingHeaders()`). Only group members will be able to write to that address, and Listig relays the reply. Use cases: a shared contact address (`kontakt@`) that a group answers from, and protecting members' addresses from each other.

- Both modes use a **single** token address (no second `Reply-To` address — not all mail clients handle several). The copy to the group for `masked-both` is made server-side when the reply arrives, so unlike `both` no member-sender exemption is needed (the replier is excluded from the group copy).
- `ReplyTargetStore` (`src/Mail/ReplyTargetStore.php`, table `reply_targets`, migration 007): one row per `(list_cn, kind, target_key)`. `kind = member` stores the member's `username` attribute if present (LDAP: `cn`), else the address, and is resolved live against the current members when a reply arrives — an address change is followed automatically (with a `username`). `kind = external` stores the address. The token carries no expiry: the row is the boundary, so a `member` token (address in old mails, address books) stays valid as long as the member is on the list (a member who left no longer resolves). Only `external` rows unused for `ReplyTargetStore::MAX_AGE_DAYS` (180) are purged in the worker cleanup step.
- **Tokens are list-specific**: a separate row (hence token) per list for the same address; the payload carries `ListFingerprint`, and `ReplyTargetStore::find()` always looks up `(id, list_cn)` of the list the mail arrived on — the database check is the real boundary.
- **Receiving** (implemented): `ReplyTargetStore::extractToken()` reads `{localPart}+r-{TOKEN}@` from the *raw* To (fallback Delivered-To/X-Original-To) header — not `$mail->to`, which PhpImap lowercases (same reason as accept/reject). `IncomingMailFilter` step 7 then applies `checkMaskedReply()` instead of `checkPostAccess()` (skipped for `type: subaddress` lists): `restricted-members:` → `reject.sender_restricted`; sender not member/owner/`senders:` → `reject.reply_not_allowed`; token invalid/expired/other list/target gone → `reject.reply_target_unknown`. `post-access-members` (`deny`/`moderate`) applies only to `masked-both` (whose reply also reaches the group); `masked-sender` reaches one person and is never moderated. Size, SPF/DKIM and rate limit apply as always.
- **Relay** (`MailProcessor::process()`): the target is resolved live (`ReplyTargetStore::resolve()` → `ReplyTarget`, a member by `username` else address, owners included). Recipients (`resolveReplyRecipients()`): `masked-sender` → only the target; `masked-both` → the group minus the replier, plus an external target. Receive restrictions and bounce suppression apply to the target too. The mail goes out `From: <list address>` with `smtp-from-name`; its `Reply-To` is again the replier's own token (an anonymous back-and-forth between members). The visible To/Cc has the token address replaced by the list address (`replaceTaggedAddressInRecipients()`). An **external** target gets a plain copy (`$externalEmail`): no list label, footer, `List-*`/`Precedence` headers, `Reply-To: <list address>` — an outsider can't use a token, so their answer goes through the normal list pipeline (`post-access-public`). A successful use touches `last_used_at`.
- **Archive**: a private reply (`masked-sender`, or any relayed reply on a `sender`/`both` list — `ReplyToBehavior::relayMode()` is `MaskedSender`) is private — `bin/worker.php` deletes it from IMAP outright (`ImapArchiver::delete()`, regardless of the list's `archive:` setting) and skips `ArchiveIndexer::index()` (`ReplyTargetStore::isPrivateReply()`), so it is kept neither on IMAP nor in the web archive. Likewise a *rejected* mail to a `+r-` address (`ReplyTargetStore::isReplyMail()`) is deleted, not archived. `masked-both` replies are indexed like any distributed mail.
- **Web form for a first mail to an external address** (`GET /{listname}/compose`, `ComposeController`, `templates/compose.latte`, `public/assets/compose.js`; API `POST /_/api/compose/{listname}` behind `AuthMiddleware` + CSRF): the member enters the recipient, the server issues the signed `{localPart}+r-{TOKEN}@{domain}` address (`ReplyTargetStore::tokenFor()`) and returns a `mailto:` link, which `compose.js` shows in a `<dialog>` (the address as a clickable `mailto:` link plus a copy button, `navigator.clipboard` with a select-and-`execCommand` fallback) instead of opening the mail client right away — so the address can also be pasted into another mail program. Listig sends nothing itself; the normal reply pipeline then relays the mail From the list address, with a plain copy for the external (its answers go to the list). Available only when `ListConfig::canComposeExternal($identity)`: a masked reply-to mode **and** `post-access-public` != `deny` (else the external's answer would be rejected); owners and `senders:` always, members unless `masked-both` combines with `post-access-members: deny` (masked-sender never reaches the list); never a `restricted-members:` sender. Otherwise 404 and the links (dashboard, `/{listname}` info and manage page) are hidden. Rate-limited to 20 per 10 minutes and user; the address must be valid, not the list's own and not `.invalid`. Deliberately no list of previous contacts — it would reveal external addresses to members who never dealt with them.
- `sender-address-header` (`never` default, `external`, `always`) adds `X-Original-Sender-Address` for members who need the real sender; headers are rarely visible in mail clients — the footer variable `{sender-mail}` is the visible alternative. Either exposes the address to every member; document this in a privacy policy.

## Masked From address

`from-address: masked` (default `list`) puts the sender's own `{localPart}+r-{TOKEN}@{domain}` address into From (display name unchanged); `Reply-To` is set per `reply-to` as before, so "Reply" still follows it while "reply to sender" / address-book use of the From reaches the sender through the private relay in every mode. Tokens do not expire ([ADR-0017](../adr/0017-masked-reply-addresses.md)); external posters (`senders:`, non-members) are masked too, their row is purged after 180 unused days. A relayed reply's From is the replier's address; an external target gets the list address (it cannot use a token). Not applied on `type: subaddress` lists. The From is aligned with the sending domain, so DMARC is unaffected; recipients filtering on `From: list@…` must filter on `List-Id` instead. The address is a stable pseudonym per sender and list.
